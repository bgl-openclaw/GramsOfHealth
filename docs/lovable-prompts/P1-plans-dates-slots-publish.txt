Grams Editor — P1: plans for full clients — dates & day types, the client's own meal slots, quarter serves, Draft → Published (owner-approved)

Background: today plan days are just "Day 1, Day 2…", every day uses the client's Default targets, the slots are always Breakfast/Lunch/Dinner/Snacks, half serves can't be saved (the column was whole numbers), and a sent plan silently changes when a recipe is edited. The database is done (migration 0037) — do NOT create migrations. Do NOT edit src/lib/engine.ts, src/lib/adjust.ts or src/lib/energy.ts. Every RPC below returns { ok, message, … } for expected refusals — show `message` when ok is false; never assume success.

DATABASE (already live)
- meal_plans: new start_date (date | null) and status ('draft' | 'published'). status changes ONLY through the RPCs below (a direct update is refused).
- meal_plan_items.servings_override is now a decimal in steps of 0.25 (1, 1.25, 1.5 …); other values are refused.
- meal_plan_days (meal_plan_id, day, day_type): per-day day-type OVERRIDES only. Delete the row to go back to the weekly pattern.
- rpc plan_days(p_plan_id) → one row per day: day, date (null without a start date), weekday ('Mon'…), day_type ('default'|'hard'|'moderate'|'rest'), day_type_source ('override'|'weekly pattern'|'default'), targets_day_type (which targets were used — 'default' when that day type has none; null when the plan has no client/targets), kcal, protein_g, carb_g, fat_g, fibre_g.
- rpc plan_slots(p_plan_id) → position, name, slot_kind ('breakfast'|'lunch'|'dinner'|'snack'|null), free_choice, source ('client'|'default'|'item'). Client slots in the client's order; the default four when there's no client (or the client has none); plus any slot name an item still uses.
- rpc plan_publish_check(p_plan_id) → { can_publish, blockers: [text], needs_review: [recipe titles], next_version }.
- rpc publish_meal_plan(p_plan_id, p_snapshot jsonb) → { ok, version_no, needs_review, message }. The database checks the snapshot matches the saved plan (see section 4) and records the Needs-review recipes itself.
- rpc start_new_plan_version(p_plan_id) → { ok, message }. Plan goes back to draft; the last published version stays "the published version" until you publish again.
- meal_plan_versions (read-only): id, meal_plan_id, version_no, snapshot, needs_review_recipes, published_at, published_by_name.
- While a plan is published the database refuses: adding/editing items, day-type overrides, start date / days changes. Title and notes stay editable. Item DELETE is allowed (so deleting a recipe still works) — but the UI must not offer it on a published plan.
- Deleting a plan that has published versions is dietitian/admin only (interns get a refusal message); it removes the versions too.
